# 基础设施：存储、索引与协议

**研究日期：** 2026-11-01

这份文档之上的所有内容都在讲记忆应该做什么。这一篇讲真正建起来的时候哪里会坏。

核心主张有点不好听：**agent 记忆系统的几乎每一个生产事故，都是存储层的事故，不是模型的。** 检索返回了错的东西，因为过滤加在 top-k 之后。记忆静默消失了，因为索引超了预算被截断。租户看到了别的租户的数据，因为隔离只是一个共享 collection 上的 `WHERE`。删除没有真删，因为向量还在 HNSW 图里。

这些都不是推理问题。它们全都是"基准上分数很好、生产里不能用"的原因。

---

## 1. 这套栈到底是什么

一个 agent 记忆系统不是一个数据库。它至少是六样东西，而它们会各自独立地坏。

| 层 | 职责 | 常见选择 | 失败模式 |
|---|---|---|---|
| **事件日志** | 发生了什么 的持久记录 | 只追加表、对象存储、Iceberg | 压实丢掉来源 |
| **派生存储** | 抽出的事实、实体、摘要 | Postgres、文档库 | 与日志漂移；没有重建路径 |
| **向量索引** | 相似度检索 | HNSW / IVF / DiskANN | 过滤下召回坍塌 |
| **词法索引** | 精确匹配与罕见词 | BM25、FTS5、Tantivy | 跨会话词表不匹配 |
| **图** | 关系、多跳 | 属性图、RDF | 边过期；遍历无界 |
| **上下文组装器** | 挑选并排序进入提示的内容 | 应用代码 | 位置效应、预算溢出 |

**架构要点。** 日志是唯一必须持久的东西；其余都可推导。做对这一点的系统，在换嵌入模型之后可以重建索引。没做对的，就永久绑在第一个模型选择上，而这个耦合只有在想升级的时候才看得见。

这跟 [01-human-memory.zh-CN.md](01-human-memory.zh-CN.md) 第 1 节的"存储强度 vs 提取强度"是同一个区分，只是搬到了基础设施上：日志是你仍然拥有的，索引是你当前够得到的。重建是"从保留的痕迹重新学习"在工程上的对应物，而它只有在痕迹被保留时才可能。

## 2. 向量索引：三方权衡

每个近似最近邻结构都在 **召回**、**延迟**、**内存** 三者之间做交易，而三者不可兼得。知道自己放弃了哪一个，就是全部的技术含量。

### HNSW

Malkov, Y. A., & Yashunin, D. A. (2020). Efficient and robust approximate nearest
neighbor search using Hierarchical Navigable Small World graphs. *IEEE TPAMI*,
42(4), 824–836. DOI
[10.1109/TPAMI.2018.2889473](https://doi.org/10.1109/TPAMI.2018.2889473)。

一张多层邻近图：稀疏的上层做长跳，稠密的下层做局部精修。搜索从顶层贪心下降。三个参数要紧：

`M` —— 每个节点的边数。越高召回越好、内存越多；典型 16–64。
`efConstruction` —— 构建时的候选表大小。越高图越好、摄入越慢。
`efSearch` —— 查询时的候选表大小。越高召回越好、延迟越差，而且**它是三者中唯一能在查询时改的**。

两个对记忆系统特别要紧的性质。

*HNSW 不擅长删除。* 删一个节点意味着修复它的邻域，或者留一个搜索仍会经过的墓碑。多数实现是打墓碑然后周期性重建。这就是为什么向量库里的"删除"通常是"标记然后稍后压实"，也是为什么可证明的删除（[06-security.md](06-security.zh-CN.md)）很难：载荷可能没了，而图仍然编码着它的存在。

*HNSW 对重复是优雅退化，但不是单调的。* 近重复的嵌入挤成稠密区域，图搜索把预算耗在那里。索引前先去重不是优化，是召回要求。

### IVF 与量化

**IVF** 用 k-means 把空间分成若干格，只搜最近的 `nprobe` 个格。构建便宜、增量更新容易，但召回在格子边界掉得很厉害，`nprobe` 必须按数据集调。

**乘积量化（PQ）** 把每个向量压成一串质心 ID，用精度换内存。**标量量化**（int8）是 4 倍压缩、损失不大，通常是对的选择。**二值量化**是 32 倍、损失很大，只有在配重打分时才可用。

大规模下占主导的组合是 **IVF + PQ** 或 **HNSW + SQ**，而实践规则是：量化误差可以接受，**前提是你对 top 候选做精确重打分**。重打分几乎所有人都忘了的便宜修正。

### GraphANN 那个观察

磁盘型图索引（DiskANN 及其所用的 `Vamana` 图）之所以存在，是因为到某个规模索引装不进内存了，而一个溢到 swap 的内存 HNSW 比一个设计良好的磁盘驻留图更慢。Subbareddy, S., et al. (2019), *DiskANN: Fast Accurate Billion-point Nearest Neighbor Search on a Single Node*, NeurIPS。

实用的阈值：100 万条 × 1536 维 float32 的 HNSW 在算上开销前约 6 GB，装得下。到 1 亿就装不下了，设计选择整个变了。

## 3. 过滤：召回静默死掉的地方

这是 agent 记忆基础设施里后果最大、讨论最少的一个细节，值得讲精确。

一个记忆查询几乎从不是纯相似度。它是"与这个查询相似，**且**属于这个用户、在这个项目里、未被标记失效、创建于日期 D 之后"。这些是过滤条件，而你在**哪一步**应用它们，会完全改变答案。

**后过滤（朴素做法）。** 先在索引里搜 top-k，再丢掉不满足过滤的结果。问题：如果过滤只选中语料的 1%，全局 top-k 里几乎没有相关条目，查询返回两条而不是十条。召回在*过滤最有选择性时*坍塌向零——也就是多租户场景，也就是正确性最要紧的时候。

**前过滤（精确）。** 先算出过滤集，只在匹配子集里搜。正确，但它毁掉索引：HNSW 没法高效地在任意子集上搜索，于是实现要么回退到对子集暴力扫（小子集没问题，大子集灾难），要么为每个过滤值建一个独立索引（值少可以，几百万用户不可能）。

**单阶段过滤搜索。** 正确答案，也是现代引擎实现的方式：遍历图，但只接受通过过滤的节点，并把候选表放大以补偿。召回得以保持，代价是查询变慢，而性能随过滤选择性退化得**可预测**，而不是灾难性地。Qdrant 把这叫 filtered HNSW 并明确文档化了这个权衡（[qdrant.tech/documentation/concepts/filtering](https://qdrant.tech/documentation/concepts/filtering/)）；pgvector 把它暴露成迭代索引扫描（[github.com/pgvector/pgvector](https://github.com/pgvector/pgvector)）。

**设计规则。** 如果你的过滤选中语料不到约 10%，而你在做后过滤，那你有一个正确性 bug，它会在多用户场景里表现为"助手记不住东西"，而在 demo 里永远不出现，因为 demo 只有一个用户。

**这对 agent 记忆特别意味着什么。** agent 记忆*本质上*是重过滤的——按用户、按项目、按 agent、按有效期、按时间。它对朴素向量库是最糟糕的负载，而多数 agent 框架用的恰好就是那个。这也是"索引加文件"架构（[03-agent-native-memory.zh-CN.md](03-agent-native-memory.zh-CN.md) 第 2 节）表现更好的原因之一：文件系统*全是*前过滤，而且过滤是免费的，因为路径就是过滤。

## 4. 混合检索：词法加向量

纯向量检索恰恰在 agent 最关心的查询上失败：标识符、错误码、函数名、专有名词、稀有词。`ERR_CONN_RESET` 没有有用的嵌入。纯词法检索在转述上失败。每个认真的记忆系统都跑两者并做融合。

**倒数排名融合**（RRF；Cormack, G. V., Clarke, C. L. A., & Büttcher, S. (2009), *Reciprocal rank fusion outperforms Condorcet and individual rank learning methods*, SIGIR）是默认，因为它参数少、鲁棒：

```
score(d) = Σ_r  1 / (k + rank_r(d))
```

常数 `k = 60` 是惯例。它只用排名，所以不需要两个系统之间的分数校准——这是它的长处，因为余弦相似度和 BM25 分数不可比，也永远不会可比。

**分数融合**（归一化后相加）在能校准的时候更好，不能校准的时候更差。实践上多数团队从 RRF 开始，然后就留在那里。

**两者共有的失败模式。** 融合可能把一个在两个信号上都平庸的文档，排到一个在其中一个信号上极好的文档上面。RRF 的 `k` 控制单个强信号能有多主导；小 `k` 奖励单信号，大 `k` 向共识压平。`k = 60` 是妥协，不是定律。

**值得知道的细节。** RRF 是基于排名的，所以它**丢弃了量级**——余弦 0.95 的第 1 名和余弦 0.55 的第 1 名完全一样。对 agent 记忆来说，"这是用户的名字"和"这和名字有点关系"的差别正是量级，这个损失是要紧的。实用的修法是混合：用 RRF 定候选集，再用交叉编码器或原始分数做最终排序。

## 5. 选存储：诚实的对比

| 选项 | 向量 | 词法 | 图 | 事务 | 适合 | 不适合 |
|---|---|---|---|---|---|---|
| **PostgreSQL + pgvector** | HNSW / IVFFlat | `tsvector` + GIN | 递归 CTE | 有 | 一个必须正确的系统 | 向量数量极大；过滤召回要调 |
| **SQLite + FTS5 + sqlite-vec** | 暴力 / 小型 HNSW | FTS5 BM25 | 无 | 有 | 单 agent、本地、可移植 | 超过约 100 万向量 |
| **Qdrant / Weaviate / Milvus** | 一等 HNSW + payload 过滤 | 各异 | 各异 | 有限 | 重过滤的专用向量负载 | 不能当记录系统 |
| **Neo4j / Memgraph** | 次要 | 次要 | 一等，Cypher | 有 | 关系重的记忆（Zep 那种） | 向量召回；运维成本 |
| **Elasticsearch / OpenSearch** | 次要（kNN） | 一等 BM25 | 无 | 有限 | 文本重、已有这套基础设施 | 一致性；成本 |
| **ClickHouse** | 实验性 | tokenbf / ngram | 无 | 无 | 只追加的事件分析 | 点更新 |
| **Iceberg + Trino/Spark** | 无 | 无 | 无 | 无（表上有 ACID） | 持久日志；重放与重建 | 任何交互式场景 |

**三条真正是观点的建议。**

*从 Postgres 加 pgvector 开始。* 一个系统、真事务、真过滤、真连接，还有一个会在你做蠢事的时候告诉你的查询规划器。几乎每个 agent 实际运作的规模它都扛得住。等你有了测量出来的理由再走。

*把日志和索引分开。* 一张只追加的表（或带 manifest 的对象存储），记录每一次写入，包括被取代的那次。索引可重建；日志不可。这是嵌入模型迁移、索引迁移和审计之所以可能的前提。

*不要为了图去用图数据库。* 对多数 agent 记忆，你需要的关系很浅（一到两跳），查询也很简单。一张带正确索引的 `relations` 表在成本和运维上都优于图数据库，直到你真的需要变长路径查询——那时候你会知道，因为你会写出那个递归 CTE 并撞到它的极限。

## 6. 时间建模

三种设计，正确性和成本递增。

**覆盖。** 更新那一行。最便宜，也失去了回答"上周我们相信什么"的能力。几乎每个早期记忆系统都这么做，然后解释不了一个错误答案。

**带墓碑的软删除。** 留着行，设 `deleted_at`。能回答"这曾经是真的吗"，不能回答"它什么时候不再是真的"，而且让删除更难（[06-security.md](06-security.zh-CN.md)）。

**双时间。** 每条事实两个时间轴：**有效时间**（它在世界上何时为真）和**事务时间**（系统何时记录它）。矛盾时设 `t_invalid` 而不是删除；按任一轴做"截至"查询。这是 Zep / Graphiti 实现的模型（[04-research-architectures.zh-CN.md](04-research-architectures.zh-CN.md) 第 4 节），也是正确的模型。

双时间值得这个成本的理由：它是唯一能回答 agent 真正会被问到的三个问题的设计。*我现在知道什么？* 过滤 `t_invalid IS NULL`。*我回答那个的时候知道什么？* 按事务时间过滤。*那时候世界上什么是真的？* 按有效时间过滤。单时间戳的 schema 只能回答三个中的一个。

**适配 Postgres 的实现。** 两个 `timestamptz` 列，加上 `(entity_id, tstzrange(valid_from, valid_to))` 上的排他约束，就是全部。在你需要之前它几乎不花成本——而这就是从第一天就做它的理由。

## 7. 多租户与隔离

记忆是按用户、按项目、按 agent、有时按 worktree 的（[03-agent-native-memory.zh-CN.md](03-agent-native-memory.zh-CN.md) 第 5 节）。把隔离做错是数据泄露，不是 bug。

**三个层级，以及取舍。**

*每租户一个 collection / schema / database。* 隔离完美，删除简单（drop 掉），租户数大时昂贵——每个 HNSW 索引有固定开销，一万个租户各一万条向量就是一万个小索引和大量浪费。

*共享 collection 加租户字段。* 高效，也是唯一能扩展到消费级租户数的设计。要求**每一个**查询都严格过滤，并继承第 3 节的后过滤召回坍塌。

*行级安全。* Postgres RLS 给你共享 collection 的效率加上强制隔离——策略由引擎施加，所以漏写一个 `WHERE` 是权限错误而不是泄露。这是目前最好的折中，而在 agent 框架里被严重低估。

**最要紧的规则。** 隔离必须在应用忘不掉的那一层强制。应用层的 `WHERE tenant_id = ?` 是一个约定；数据库策略是一个不变量。前者会产生事故。

## 8. KV cache 作为一层记忆

这是本文档里最被低估的一条洞见。

一个 transformer 对某段前缀的 KV cache，是**对该前缀的可复用计算，按内容寻址**。如果两个请求共享前缀，第二个可以完全跳过 prefill。厂商对这件事明码标价——缓存输入 token 的价格是不缓存的一小部分——而折扣大到足以让前缀设计本身成为一门优化手艺。

**为什么这属于一篇记忆文档。** MemOS 把激活记忆当作与明文和参数并列的一等记忆基底（[04-research-architectures.zh-CN.md](04-research-architectures.zh-CN.md) 第 4 节），它是对的。一条 KV cache 条目就是一个记忆：它编码内容，可以被存储和重载，而持有它就是快系统与慢系统的差别。

**设计上的推论。****把稳定的内容放前面。** 系统提示、指令、记忆索引、检索到的材料、查询。第一个易变 token 之前的一切都可跨请求缓存；它之后的一切都会让缓存失效。一个把时间戳注入到提示顶端的记忆系统，让整个提示不可缓存，而且毫无理由。

这是真实的成本：在规模上，可缓存与不可缓存的提示差的是账单的一大截。而它完全是一个*排序*决定，也就是说做对不花钱，做错了又看不见。

## 9. 协议：什么在被标准化，什么没有

记忆没有标准，而存在的那些标准是为相邻问题写的。这是 2026 年底的状态。

### MCP

Model Context Protocol 标准化模型如何触达工具和资源。它的 **2026-07-28 修订取消了会话**——协议现在是无状态的，意味着记忆服务器不能假设调用之间的连续性，必须把一切键控在请求里显式传入的标识符上。

后果是真实且大多没有被评论的：**MCP 本来是标准记忆接口的自然位置，而无状态修订把这扇门关上了。** 一个跑在 MCP 上的记忆服务器是一个带工具形状 API 的数据库，不是一个记忆。每个实现做的都是同一件事——在自己的服务器里重新实现抽取、整合和检索，零互操作。

### A2A

Agent2Agent 协议标准化 agent 之间的委派。它**明确不共享记忆**——规范里声明了这一点，设计上给每个 agent 自己的上下文。

这是一个决定，在安全上是站得住的。它同时也意味着一个 agent 团队无法积累共享知识，而唯一共享的方式是一个 agent 发消息给另一个、后者把它存为自己的记忆——过程中丢掉来源。

### AGENTS.md

一个约定，不是一个协议：仓库根目录的一个 Markdown 文件，编程 agent 把它当指令读。它覆盖了 6 万多个开源项目，并被捐赠给 Linux 基金会的 Agentic AI Foundation，这使它成为所有类型的 agent 标准里采用最广的一个。

它对记忆的意义是负面的：它标准化了**指令**层，把记忆层留成了未标准化。这就是为什么 [03-agent-native-memory.zh-CN.md](03-agent-native-memory.zh-CN.md) 里每个产品在共享一个指令格式的同时，各自独立地重新实现记忆。

### 停滞的那些尝试

IETF 的 `aimem-bundle` 草案提出一个可移植的记忆容器格式。W3C 的记忆互操作社区组在讨论同一个问题。两者都存在；都没有采用。**Agent Memory Repo**（Devin 的规范：一个 git 仓库，`MEMORY.md` 作入口，单行条目带 `[source: …; added: …]`，文件间用 `[[path]]` 链接）是唯一背后有已上线实现的格式，而它是某一家厂商的。

**诚实的评估。** 记忆互操作不会靠一个协议解决，直到某人有产品理由让他们的记忆可导出。Claude 和 Kimi 已经在提供导入导出；压力来自那里，而那是消费者保护的压力，不是工程的压力。

## 10. 失败模式，按发生频率排序

**1. 后过滤召回坍塌。** 第 3 节。存在于多数 agent 框架。一个用户时看不见，多个用户时是灾难。

**2. 没有重建路径。** 索引是唯一副本，嵌入模型被弃用，没有办法迁移。每个只存了嵌入、没存源文本的系统都处在这个状态。

**3. 静默截断。** 索引超出预算，最旧的条目被丢掉，日志里一行都没有。每个有预算的产品都有某个版本的这个（[03-agent-native-memory.zh-CN.md](03-agent-native-memory.zh-CN.md) 第 7 节）。

**4. 无界遍历。** 图检索一直扩张，直到撞上整张图的邻域。HippoRAG 的 PageRank 构造上就有界；手搓的图记忆通常没有。

**5. 重复泛滥。** 同一条事实写了一百遍，填满 top-k 并把其他一切挤出去。解法是写入时去重，而几乎没人做，因为它要求每次写入都做一次相似度检查。

**6. 时间戳当有效性。** 用 `created_at` 决定现在什么是真的。这就是为什么系统坚持用户还住在两年前提过的那个城市。

**7. 敌视缓存的提示组装。** 第 8 节。花钱，而且没人发现。

**8. 没删掉的删除。** 第 6 节与 [06-security.md](06-security.zh-CN.md)。软删除的向量仍然含有语义信息，HNSW 图仍然编码着它的邻域。

## 11. 如果你在建这个东西

一个简短、有立场的顺序。

**先把原始事件存进一张带单调 ID 的只追加表。** 在你有任何 schema 意见之前就做。这是唯一一个反转代价昂贵的决定。

**把抽出的事实放进 Postgres，两个时间戳列加一个 `t_invalid` 范围。** 第一天就双时间；不花成本，换来那三个要紧的查询。

**在事实表上加 pgvector，过滤列建好索引。** 过滤查询用迭代索引扫描；上线前在 1% 选择性的过滤查询上验一遍召回。

**加 FTS5 或 `tsvector` 做词法，用 RRF 融合。** 然后对 top 20 做精确重打分。

**把产品们建的那个索引建出来。** 一个有硬预算的 `MEMORY.md`，后面是主题文件，每条带一行 `[source: …; added: …]`。它简单、有效，花一个下午。

**稳定内容放提示前部，易变内容放后部。** 然后测你的缓存命中率，你会吃惊。

**在你需要之前把重建脚本写好。** 一个函数，吃事件日志、产出存储，能从头跑。如果你不能重建，你就没有拥有你的记忆。
